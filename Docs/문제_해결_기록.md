- 1판: 로비 → 출정 → 전투 씬, 이어서 DECK 버튼 → 패배 → "작전 실패" 화면 → 기지로 귀환 → 로비
- 2판: 다시 출정 → 전투 씬, 이어서 패배 → 귀환

매 단계에서 확인한 값:
- 새 GameManager가 생기고 HP는 80
- 축복 화면이 열림
- 덱은 13장이고 파괴된 카드 0장
- 협력자는 3명
- 층은 0으로 초기화
- 로비 매니저가 살아 있음

## 원인: 매니저 여러 개가 한 오브젝트에 붙은 채 DontDestroyOnLoad

전투 씬의 `GameplayManager` 오브젝트 하나에 컴포넌트 8개가 붙어 있다.

```
GameManager · BattleManager · MapManager · MapUIController
CooperationManager · HolyPlaceManager · DeckManager · ItemInventoryManager
```

이 중 GameManager·MapManager·CooperationManager·HolyPlaceManager·DeckManager가 각자 `DontDestroyOnLoad(gameObject)`를 불렀다. `DontDestroyOnLoad`는 **오브젝트 전체**에 걸리므로, 씬을 넘을 때 8개가 전부 살아남는다.

중복을 처리하는 코드도 전부 `Destroy(gameObject)`였다. 그래서 컴포넌트 하나가 "나는 중복"이라고 판단하면 같은 오브젝트의 나머지 7개까지 함께 지웠다. 이 구조 때문에 생긴 증상은 이렇다.

| 경로 | 증상 |
|---|---|
| 로비 → 전투 | 로비의 DeckManager가 먼저 살아 있어서 전투 씬 DeckManager가 오브젝트째 자폭 → GameManager까지 사라져 런이 시작되지 않음 (HP 0/80, 빈 화면) |
| 전투 → 전투 (다시 시작) | 이전 런의 GameplayManager가 살아 있어서 새 것이 자폭 → 이전 런 매니저들이 사라진 씬의 UI를 가리킴, `InitializeRun`도 안 돎 |
| 로비 → 전투 (DECK) | DECK 버튼이 전투 씬 DeckManager 컴포넌트의 `ViewDeck`을 직접 부르는데 그 컴포넌트가 지워져서 무반응 |
| 로비 → 전투 (협력자) | 로비의 CooperationManager(Cp_01만 등록)가 살아남고 전투 씬 것(Cp_01~03)이 지워짐 |

## 해결: 수명이 다른 것끼리 나눈다

**런 씬 전용 — 씬마다 새로 만든다** (`DontDestroyOnLoad` 제거)

| 스크립트 | 변경 |
|---|---|
| `GameManager` | `Awake`에서 `Instance = this`, `OnDestroy`에서 자기면 null. 씬을 다시 불러오면 새 인스턴스의 `Start` → `InitializeRun`이 새 런을 연다 |
| `MapManager` | 같음. 맵은 `InitializeRun` → `InitializeMap`에서 다시 만든다 |
| `HolyPlaceManager` | 같음 (CP949 인코딩 파일이라 인코딩 유지해서 수정) |

**씬을 넘어 유지할 데이터 — static에 두고 컴포넌트는 창구로**

| 스크립트 | 변경 |
|---|---|
| `DeckManager` | 덱 목록을 `static s_playerDeck`으로. 컴포넌트는 씬마다 하나씩 있고 가장 최근 것이 `Instance`. 처음 한 번만 시작 덱을 만든다. DECK 버튼이 부르는 이 씬의 컴포넌트도 살아 있으므로 버튼이 동작한다 |
| `CooperationManager` | 호감도 상태 `coopCharDict`를 static으로. 각 씬 컴포넌트가 `Awake`에서 자기 `coopCharList`를 **합친다**(이미 있는 캐릭터의 호감도는 건드리지 않음). 로비에 Cp_01만 있어도 전투 씬에서 Cp_02·03이 더해진다 → 문제 1 해결 |

두 스크립트 모두 `RuntimeInitializeOnLoadMethod(SubsystemRegistration)`로 static을 비운다. 에디터에서 도메인 리로드를 끄더라도 이전 플레이의 데이터가 남지 않게 하려는 것이다.

`RunData`, `QuestManager`, `BlessingAffinityManager`는 자기 전용 오브젝트에서 `DontDestroyOnLoad`를 쓰므로 그대로 뒀다. 다만 RunData의 런 단위 값인 `cardRemoveCount`는 `InitializeRun`에서 0으로 되돌린다.

## 두 번째 런에서 축복 화면이 안 열리던 문제

**원인:** `GameManager.InitializeRun`이 `BlessingView.Instance ?? FindObjectOfType<BlessingView>(true)`로 뷰를 찾았다.
- BlessingView는 비활성으로 시작해서 `Awake`가 아직 안 돌았다. 그래서 `Instance`에는 **이전 런 씬의 파괴된 뷰**가 남아 있었다.
- C#의 `??`와 `?.`는 Unity의 파괴된 오브젝트를 null로 보지 않는다. 그래서 파괴된 뷰에 `Open()`을 호출했다.

**해결:**
- GameManager는 `== null` 비교로 거르고, 없으면 `FindFirstObjectByType(Include)`로 찾는다.
- 비활성으로 시작할 수 있는 뷰들에 `OnDestroy`에서 `Instance`를 비우는 코드를 넣었다: BlessingView, CardListView, EventView, BossBattleDirector, MapUIController, ItemInventoryManager.
  - `StatusTooltipView.Instance?.Show…` 같은 호출이 파괴된 이전 뷰를 부르지 않게 된다.

**앞으로:** `static Instance` 싱글톤을 새로 만들 때는 `OnDestroy`에서 `if (Instance == this) Instance = null;`을 넣는다. Unity 오브젝트에는 `??`와 `?.`를 쓰지 않는다.

## 문제 3: 전투 → 로비 귀환

- `RunClearView`가 런 클리어와 **패배** 두 경우에 뜨도록 바꿨다.
  - 패배는 `BattleManager.OnBattleDefeat` → `defeatDelay`(2.2초, "작전 실패" 배너가 끝나는 시점) 뒤에 뜬다.
  - 제목은 "작전 실패", 부제는 "N막 N층에서 쓰러졌습니다"이다. 이전에는 패배 시 아무 화면도 없었다.
- 버튼을 "다시 시작" → **"기지로 귀환"**으로 바꿨다.
  - `SceneTransition.Load(lobbySceneName, "귀환", "기지로 복귀합니다", "RETURN  //  BASE")`로 귀환 문구 전환 막을 거쳐 로비로 간다.
  - 로비 씬이 빌드에 없으면 예전처럼 현재 씬을 다시 연다.
- 인스펙터 값: `lobbySceneName`(기본 "Lobby"), `defeatDelay`.

귀환하면서 같이 고친 것:

| 문제 | 해결 |
|---|---|
| 덱이 씬을 넘어 유지되므로 귀환 후 지난 런 덱이 남음 | `LobbyManager.Start`에서 `DeckManager.InitializeStartingDeck()` |
| `UserExpManager`가 로비에 들어올 때마다 기본 경험치로 초기화 → 의뢰 보상 경험치가 다음 귀환 때 사라짐 | PlayerPrefs(`VERTEX_USER_EXP`)에 저장·복원. 디버그 "Reset Experience"도 저장값을 기본값으로 덮는다 |

## 문제 6: 작전 개시 배너 위로 적 툴팁

`BattleOperationFx`의 가운데 배너(작전 개시·종료·실패)에만 자체 Canvas를 달아 `bannerSortingOrder` = **210**으로 올렸다. 적 인텐트/상태 툴팁(200)보다 위다.
카드 컷인과 적 처치 기록은 덱 목록(99) 아래여야 하므로 90에 그대로 뒀다.

## 문제 7: 제파러 공격 프레임 — 코드로 고칠 대상 아님

공격 시트 16프레임의 캐릭터 높이(프레임 1216px 중):

```
630 699 659 630 742 674 661 615 682 699 679 734 710 609 610 610   (중앙값 667, 대기 785)
```

- 대기와 공격 사이 **여백 차이**는 이미 보정하고 있다. `attackSheetPadding` 0.40 대 `idleSheetPadding` 0.27이라 공격 중 ×1.17이다.
- 남은 차이는 공격 동작 자체(웅크림 609 ↔ 뻗음 742, ±10%)에서 온다.
- 프레임마다 크기를 맞추면 웅크리는 동작이 사라지고 캐릭터가 출렁인다. 그래서 코드로 억지 보정하지 않았다.
- 거슬린다면 시트를 다시 뽑을 때 기준 포즈(선 자세)의 크기를 대기 시트와 맞춘다. 여백 규칙은 대기 1할, 공격 3할이다.

## 문제 8: 에디터 셋업 스크립트의 옛 폰트

`BlessingUISetup.cs`와 `SanctuaryDetailSetup.cs`가 `강원교육튼튼 SDF` 경로 대신 `TMP_Settings.defaultFontAsset`(현재 Pretendard Bold)을 쓴다.

## 남은 것

- `RunClearView` 제목이 노란색이다. 아트 디렉션(빨강·노랑 금지)과 맞지 않지만 기존 스타일이라 손대지 않았다.
- `LobbyManager.completedRunCount`(시설 해금용 런 완료 횟수)는 저장되지 않고, 런 클리어 때 올리는 호출도 없다. 시설 해금을 런 횟수에 묶을 거면 이것도 저장해야 한다.
